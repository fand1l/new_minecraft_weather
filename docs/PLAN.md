# Vibe Weather — план реалізації (Крок 1)

Мод багатовимірної локальної погоди для Minecraft Java Edition **26.2** / Fabric.
Цей документ — **тільки план**. Коду немає. Після твого підтвердження (і вибору варіанта
локальності) починається Крок 2.

---

## 0. Що я перевірив, а що ні

### Перевірено (з першоджерела, не з пам'яті)

Моє знання обривається до релізу 26.2, тому версії я звіряв не по пам'яті, а з офіційного
шаблону FabricMC гілки `26.2` (`FabricMC/fabric-example-mod`) і з `gradle.properties`
самого Fabric API (`FabricMC/fabric`, HEAD = `0.156.0`, `minecraft_version=26.2`):

| Що | Значення | Джерело |
|---|---|---|
| Minecraft | `26.2` | template `gradle.properties` |
| Fabric Loader | `0.19.3` | template `gradle.properties` |
| Fabric Loom | `1.17-SNAPSHOT` | template `gradle.properties` |
| Fabric API | `0.156.0+26.2` | template + `fabric/gradle.properties` |
| Gradle | `9.5.1` | template `gradle-wrapper.properties` |
| Java | `25` (`options.release = 25`, `VERSION_25`) | template `build.gradle` |
| Mixin compat level | `JAVA_25`, `overwrites.requireAnnotations: true` | template `modid.mixins.json` |

Твої цифри з ТЗ повністю збіглися — жодних правок не потрібно.

**Найважливіша знахідка: мапінги.** У шаблоні 26.2 **немає** рядка `mappings "net.fabricmc:yarn:…"`
і немає властивості `yarn_mappings`. Тобто Loom 1.17 бере мапінги за замовчуванням, і код
шаблону написаний **офіційними мапінгами Mojang**. Підтверджується імпортами:

- `net.minecraft.server.MinecraftServer` + метод `loadLevel` (Yarn називав би його `loadWorld`);
- у Fabric API 0.156.0: `ServerLevel`, `ServerPlayer`, `ClientLevel`, `Minecraft`,
  `FriendlyByteBuf`, `RegistryFriendlyByteBuf`, `StreamCodec`, `CustomPacketPayload`,
  `CommandSourceStack`, `Commands`, `CommandBuildContext`, `ServerGamePacketListenerImpl`,
  `ParticleEngine` — усе це Mojang-імена.

Окремо: клас ідентифікатора в 26.2 — **`net.minecraft.resources.Identifier`**
(`Identifier.fromNamespaceAndPath(...)`), а не `ResourceLocation`. Це видно і в шаблоні,
і в `ServerPlayNetworking` з Fabric API 0.156.0. Тобто Mojang таки перейменували цей клас
у 26.x, і писати треба `Identifier`.

**Висновок:** пишемо під Mojang-мапінги (дефолт Loom 1.17). Скажи, якщо хочеш Yarn — тоді
змінюються **всі** цілі міксинів і половина імпортів, це не косметична правка.

### Не перевірено — і я не буду це вигадувати

Мережа цього середовища ріже `fabricmc.net`, `docs.fabricmc.net`, `minecraft.wiki`,
`piston-meta.mojang.com` і `linkie.shedaniel.dev` (проксі віддає 403/timeout). Тому офіційні
мапінги Mojang для 26.2 я завантажити **не зміг** і внутрішні імена Minecraft перевірити
нічим. Конкретно не підтверджені:

1. **Клас рендеру погоди.** Починаючи з 1.21.5 ванільний дощ/сніг виїхав з `LevelRenderer`
   в окремий `WeatherEffectRenderer`. Чи він так називається у 26.2 і яка сигнатура методу
   малювання — **не знаю**.
2. **Клас туману.** У 1.21.2+ це `FogRenderer` + структура `FogParameters`. Після переробки
   пайплайна в 26.1/26.2 це майже напевно змінилось — **не знаю як**.
3. **Метод просування погодного циклу в `ServerLevel`.** Історично Mojang-ім'я —
   `advanceWeatherCycle()`. У 26.2 — **не підтверджено**.
4. **Чи є ще `WorldRenderEvents` у Fabric API 0.156.0.** Я пробував дістати
   `fabric-rendering-v1/src/client/java/net/fabricmc/fabric/api/client/rendering/v1/WorldRenderEvents.java` —
   404. Модуль існує, але його переструктурували в підпакети (наприклад,
   `.../rendering/v1/hud/HudElementRegistry.java` — 200). Тобто події світового рендеру або
   переїхали, або їх зняли під час переробки пайплайна.
5. **Події туману у Fabric API.** Файлів `FogEvents` / `FabricFogEvents` за очікуваними
   шляхами немає → швидше за все API туману немає взагалі, і потрібен міксин.
6. **Blaze3D API для власного батчу текстурованих квадів у 26.2.** Це найбільша діра.
   Перехід на `RenderPipeline` / `RenderType` / `RenderState` + Vulkan-бекенд означає, що
   спосіб реєстрації власного шейдера й пайплайна майже точно інший, ніж я пам'ятаю.
7. **Ім'я реєстру фабрик партиклів на клієнті.** `ParticleFactoryRegistry` за очікуваним
   шляхом — 404; `FabricParticleTypes` (common) — 200.

### Обґрунтування частоти оновлення

| Пакет | Частота | Чому саме так |
|---|---|---|
| `RenderParamsPayload` | вхід у гру + `/reload` | Це константи з серверного конфігу (висота хмар, ширина перехідної смуги, множники). Змінюються ~ніколи. |
| `ZonesPayload` | подієво + keepalive 200 тіків (10 с) | Рух зони **лінійний і відомий** (`center0 + drift·Δt`), тому позицію слати не треба взагалі — клієнт її рахує точно. Слати треба лише появу/зникнення зони в радіусі та зміну її стану, а стани міняються раз на ~ігрову добу. Keepalive — страховка від втраченого дифа. |
| `PlayerWeatherPayload` | 40 тіків (2 с) | Авторитетна звірка + дані для `/vibeweather query` і HUD. Формула на обох сторонах однакова, тож це фактично контрольна сума, а не джерело даних. |

**Оцінка трафіку.** Дескриптор зони: `id(8) + centerX/Z(8) + radius(2) + band(2) + driftX/Z(4) + birthTick(8) + stateA(6) + stateB(6) + transStart/End(8) ≈ 52 B`.
Найгірший випадок ~16 зон у радіусі 32 чанків → **~830 B на keepalive**, тобто **~83 B/с на гравця**.
Плюс `PlayerWeatherPayload` ~20 B кожні 2 с → **~10 B/с**. Разом **менше 0.1 КБ/с на гравця** —
на порядки менше за ванільний трафік чанків. Вимога «трафік на гравця мінімальний» виконана
з великим запасом, і 50 гравців у різних кінцях карти дають ~5 КБ/с сумарно.

## 3. Локальність: три варіанти

Це головне архітектурне рішення. Прошу обрати перед написанням коду.

### Варіант A — чисте шумове поле (stateless noise)

Погода в точці = `f(worldSeed, gameTime, x, z)`: кілька шарів value/simplex-шуму на грубій
сітці, координати семплювання зсунуті на інтеграл вітру, тому поле «пливе».

- **+** Нуль пам'яті, нуль персистенції, ідеальна масштабованість на будь-яку кількість гравців.
- **+** Межі розмиті самі собою — шум неперервний, інтерполяція безкоштовна.
- **+** Найдешевший семпл: ~20 нс, можна семплити хоч щокадру в сотнях точок.
- **−** **Зон як об'єктів не існує.** Вимогу «розмір зони випадковий 64–1024 зі зміщенням до
  середини» неможливо виразити прямо — у шуму є характерний масштаб, а не список радіусів.
- **−** «Тривалість стану в середньому доба з великим розкидом», «опади рухаються переважно
  на сусідній рівень», «після дощу спершу OVERCAST» — це семантика ланцюга Маркова.
  У полі шуму її можна тільки імітувати підбором октав, і керувати нею через конфіг
  практично неможливо.
- **−** `/vibeweather set <…> [radius]` і `freeze` все одно потребують окремого шару оверрайдів.

### Варіант B — детерміновані рухомі зони на грубій хеш-сітці ⭐ (рекомендую)

Світ ділиться на макро-комірки (конфіг, дефолт 1024×1024 блоків). Для кожної пари
(комірка, епоха) з `hash(worldSeed, cellX, cellZ, epoch)` детерміновано народжується `k` зон.
Кожна зона несе **повний кортеж усіх осей**, свій радіус, свою смугу розмиття, свій вектор
дрейфу і свою часову лінію станів (Маркова, розгорнута з власного сіда зони).
Семпл у точці = зважений бленд зон, що накривають точку, з фолбеком на «ясний» ambient-стан.

- **+** Прямо виражає **всі** вимоги ТЗ: один кортеж на зону, явний розподіл радіусів
  64–1024, рух за вітром, розмита межа через `band`, стрибок через рівень як окрема
  ймовірність у ланцюгу.
- **+** **Так само stateless**, як A: зона — це функція від хеша, ніде не зберігається,
  чанки не вантажить. Гравець, що повернувся через тиждень, побачить консистентний світ.
- **+** Клієнт може відмалювати стіну дощу на горизонті: він має геометрію зон, а не
  тільки стан у своїй точці.
- **+** `/set` і `/weather` лягають природно — це просто зона з високим пріоритетом
  і терміном дії.
- **−** Дорожчий семпл, ніж A: треба перебрати 3×3 (або 5×5) комірок × кілька епох.
  Мітигується кешем `ZoneCache` — перебір раз на секунду на гравця, не щотіка.
- **−** Потрібна акуратність із «епохами», щоб зони не з'являлись ривком, і детерміноване
  правило пріоритету для зон, що перекриваються.
- **−** Дрейф зони треба обмежити (`zone_drift_scale`), інакше зона за добу відлетить на
  кілометри й радіус сканування комірок вибухне. Рішення: швидкість дрейфу зони ≪ швидкості
  «вітру» для візуалу/фізики (напр. ≤ 0.02 бл/тік → ≤ 480 блоків за добу, менше однієї комірки).

### Варіант C — жива симуляція зон навколо онлайн-гравців

Сервер тримає реальний список об'єктів-зон навколо гравців, тікає їх (таймери, Маркови),
створює й видаляє при переміщенні, зберігає у `SavedData`.

- **+** Найпростіша ментальна модель; ланцюги Маркова, таймери, `/set`, `/freeze` пишуться в лоб.
- **+** Точний контроль над кожним параметром динаміки.
- **−** **Стан залежить від того, хто був онлайн.** Зона існує тільки там, де хтось був.
  Прилетів у незвідану область — погода «народжується» під тобою.
- **−** Персистенція росте з часом і з розміром обжитої карти.
- **−** Два гравці за 10 000 блодів один від одного вимагають, щоб сервер тікав обидва
  набори зон — GC й пам'ять ростуть лінійно від кількості гравців.

### Рекомендація: **B + тонкий шар C для ручного керування**

База — детерміновані хешовані рухомі зони (B). Поверх них — маленький персистентний список
оверрайдів (максимум десятки записів) для `/vibeweather set`, перехопленої `/weather` і
`freeze`. Оверрайд — це та сама структура `WeatherZone`, просто з вищим пріоритетом і
явним часом смерті. Так ми отримуємо детермінізм і нульову вартість спокою від B,
а ручне керування — від C, без його недоліків.

### Окремо: конфлікт двох вимог ТЗ, який треба вирішити зараз

- §3 вимагає: «межа має бути **видима здалеку**, опади рендеряться в межах дальності
  промальовування, а не лише навколо гравця».
- §Технічний стек вимагає: «клієнт нічого не вигадує сам, окрім інтерполяції між
  отриманими станами».

Ці дві вимоги неможливо виконати одночасно в буквальному прочитанні: щоб намалювати стіну
дощу за 200 блоків, клієнту треба знати погоду **в багатьох точках**, а не одну свою.

Пропоную таке прочитання: сервер лишається єдиним джерелом істини — саме він вирішує, які
зони існують, які в них стани й коли ці стани міняються. Клієнт отримує **геометрію та стан
зон** і застосовує до них **ту саму формулу блендингу**, що й сервер (спільний код у
`weather/ZoneSampler`). Це не «клієнт вигадує погоду» — це інтерполяція отриманого стану
в просторі, рівно як екстраполяція позиції зони — інтерполяція в часі.

Альтернатива (строге прочитання): сервер шле клієнту готову **сітку семплів** — наприклад
9×9 точок на 512 блоків навколо гравця, ~81 × 6 B = 486 B на оновлення. Клієнт лише
білінійно інтерполює. Це буквально відповідає «клієнт нічого не вигадує», але дає грубішу
межу (крок 64 блоки), більший трафік і мильну стіну дощу.

Я рекомендую перший варіант. Це питання винесено в опитування.

## 4. Де потрібні міксини і чому

Принцип: спершу Fabric API event, і тільки якщо його немає — міксин. Нижче — повний список,
з поясненням, чому без нього не обійтись.

| # | Ціль (Mojang-мапінги) | Навіщо | Чому не можна без міксина |
|---|---|---|---|
| **M1** | `ServerLevel` — метод просування погодного циклу *(ім'я не підтверджено, п.0.3)* | Заглушити ванільні таймери дощу/грози та розсилку `ClientboundGameEventPacket` | Fabric API не має події «до тіку погоди» і не має способу вимкнути погодний цикл. Ґеймрул `doWeatherCycle` не підходить: він лишає стан замороженим, а не переданим нам, і його бачить гравець. |
| **M2** | `Level#isRainingAt(BlockPos)` | Зробити ванільний геймплей **локальним**: гасіння вогню, ріст врожаю, наповнення казана, бонус риболовлі, спавн — усе це читає саме цей метод | Це єдина позиційно-залежна точка входу у ванілі. Один міксин тут дешевший і надійніший, ніж патчити десяток систем окремо. Події для нього немає. |
| **M3** | `Level#getRainLevel(float)` та `#getThunderLevel(float)` | Затемнення неба, гучність, освітлення для спавну — усе читає ці два методи | Немає API. Без них клієнт малює наш дощ, а небо лишається ясним — розсинхрон візуалу. |
| **M4** | Клієнтський рендерер погоди *(`WeatherEffectRenderer`? — п.0.1)* | Повністю замінити малювання опадів: нахил за вітром, щільність за рівнем, дальність до render distance | Рендер погоди у ваніль зашитий і нічим не конфігурується. Fabric API рендер-подій для погоди не має. |
| **M5** | Рендерер туману *(`FogRenderer`? — п.0.2)* | Дальність видимості від опадів + незалежна вісь туману | API туману у Fabric 0.156.0 я не знайшов (п.0.5). Якщо він таки є — міксин прибираємо. |
| **M6** | `WeatherCommand#register` | Скасувати реєстрацію ванільної `/weather`, натомість зареєструвати свою з тим самим синтаксисом, що мапиться на оверрайди | Brigadier не має публічного API для видалення вже зареєстрованого вузла. Альтернатива — accessor-міксин на приватну мапу `children` у `CommandNode`, що гірше: він ліземо в чужу структуру. Скасувати реєстрацію на HEAD — акуратніше. |

**Разом 6 міксинів**, з них 4 — тонкі `@Inject(cancellable = true)` на 3–5 рядків.

### Де міксини свідомо НЕ потрібні

- **Фізика вітру.** Моби й стріли — через `ServerTickEvents.END_LEVEL_TICK` +
  публічний `addDeltaMovement`. Локальний гравець, елітри й керований човен — через
  `ClientTickEvents.END_CLIENT_TICK` на клієнті (рух гравця симулює клієнт; правити його
  з сервера означає ривки/rubber-banding).
- **Казан і сніг.** Не патчимо ванільний `tickChunk`, а **додаємо** свої додаткові спрацювання
  у власному тіку через публічні `setBlockAndUpdate` / `BlockState`. Ванільна швидкість лишається
  як є, ми лише прискорюємо — рівно як просить ТЗ.
- **Блискавки.** Не патчимо ванільний генератор (він і так мовчить, бо `isThundering()` = false
  після M1) — самі спавнимо `LightningBolt` у прогружених чанках. Це та сама ванільна сутність
  з тими самими наслідками, тобто §6 не порушується.
- **Партикли листя.** Ванільні партикли падаючого листя зносимо, змінюючи їхню швидкість —
  без нових партиклів; робиться через тік клієнта.
- **Команди, мережа, конфіг, тік** — усе через Fabric API.

## 5. Ключові механіки: як саме

### `WeatherState.sanitize()` — єдина точка інваріантів

Викликається **завжди** після будь-якої зміни або блендингу, ніде більше немає `if`-ів:

```
1. clouds < OVERCAST  →  precipitation = NONE, thunder = OFF
                          (плавно: множимо їхні float-інтенсивності на
                           cloudFactor = smoothstep(SCATTERED, OVERCAST, cloudsFloat),
                           дискретне значення падає лише коли float дійшов нуля)
2. precipitation > NONE  →  clouds = OVERCAST                    [інваріант 1]
3. thunder > OFF         →  clouds = OVERCAST, опади НЕ вимагаються [інваріант 2 — суха гроза]
4. OVERCAST + NONE + OFF — валідно, нічого не робимо              [інваріант 3]
5. fog — не чіпаємо взагалі                                       [інваріант 5]
6. wind: strength ∈ [0,1] клемпимо, direction нормалізуємо в [0,360)
```
Інваріант 4 («падіння хмарності гасить опади плавно») забезпечується саме кроком 1: дискретна
вісь падає **після** того, як float доїхав до нуля, а не одночасно з ним.

### Розподіл розмірів зон (зміщений до середини)

`radius = min + (max - min) · (u₁ + u₂ + u₃)/3`, де `u` — рівномірні [0,1].
Це Irwin–Hall n=3: дзвін із піком у центрі, хвости до країв рідкі. Кількість доданків
`zones.size_bias_samples` — у конфігу; 1 = рівномірний random, 5 = майже гаусів.

### Тривалість стану (в середньому доба, великий розкид)

`duration = base · exp(σ · gauss())`, клемп у `[min, max]`.
Дефолт: `base = 24000`, `σ = 0.6` → медіана доба, 10% станів довші за ~2.2 доби,
окремі — до `max`. Усі чотири числа в конфігу.

### Переходи опадів

Матриця ймовірностей на сусідні рівні + окрема низька `skip_level_chance` на стрибок через
рівень. Після виходу з опадів — `stay_overcast_chance` (дефолт високий), тобто світ спершу
лишається похмурим і лише потім прояснюється; `instant_clear_chance` — рідкісний прямий шлях.

### Туман

`FogRules` рахує сумарний шанс із чотирьох незалежних контекстів (кожен зі своїм шансом
і вікном у конфігу): після завершення опадів, світанок, близькість великої води,
одночасність із `DOWNPOUR`. Вісь туману лишається незалежною і може вмикатись і сама по собі.

### Вертикальна межа

`altitudeFactor = 1 − smoothstep(cloudBottom, cloudTop, y)`, де `cloudBottom` / `cloudTop` —
з конфігу (дефолти 192 / 224, бо хмари ще перероблятимуться). Множить інтенсивності всіх
осей. Вище `cloudTop` — чисте небо, як просить ТЗ.

### Нахил опадів

Кут нахилу = `atan(windStrength · maxTiltTan)`, напрямок — з осі напрямку вітру.
Реалізується як зсув верхньої пари вершин квада відносно нижньої на
`(sin(dir), cos(dir)) · height · tan(angle)`. Тобто це **геометрія меша**, а не шейдер —
тому працює і без кастомного шейдера, і при деградації під Sodium його можна вимкнути,
не ламаючи решту.

### Sodium

`FabricLoader.getInstance().isModLoaded("sodium")` → лог `WARN` при старті +
одноразове повідомлення в чат на `ServerPlayConnectionEvents.JOIN` (клієнтська перевірка,
показується один раз за сесію) + прапорець `degraded`, який вимикає нахил опадів і
власний пайплайн, лишаючи модель погоди й фізику вітру працювати.

## 6. Припущення

1. **Мапінги — офіційні Mojang** (дефолт Loom 1.17, підтверджено шаблоном 26.2). Yarn не використовуємо.
2. **Modid `vibe_weather`**, base package `com.fand1l.vibeweather`, `environment: "*"`, як у ТЗ.
3. **Nether і End** визначаємо через `Level.dimensionType().hasSkyLight()` / порівняння
   `ResourceKey` вимірів — там `ServerWeatherManager` навіть не реєструється, погоди немає взагалі.
4. **Сніг замість дощу** визначаємо ванільним способом — через температуру біома в точці
   (`Biome.coldEnoughToSnow`-подібна перевірка), з тими самими 4 рівнями інтенсивності.
5. **Ванільна `/weather clear|rain|thunder`** мапиться так:
   `clear` → `CLEAR/NONE/OFF`, `rain` → `OVERCAST/RAIN/OFF`, `thunder` → `OVERCAST/RAIN/NORMAL`,
   у радіус `command.vanilla_weather_radius` (дефолт 512) навколо виконавця, на вказану тривалість.
6. **`freeze`** заморожує лише перехід станів; зони продовжують дрейфувати (інакше «заморозити
   погоду» означало б зупинити й вітер, що суперечить осі вітру).
7. **Конфіг** — `config/vibe_weather.json`, створюється з дефолтами при першому запуску,
   перечитується на `/reload`. Невідомі поля ігноруються, відсутні беруться з дефолтів.
8. **`/vibeweather` рівень прав 2**, як у ТЗ; `query` доступний усім (це просто інформація) —
   скажи, якщо теж треба рівень 2.
9. **Кастомний партикл смуг** — одна текстура 1×N, витягнутий квад, орієнтований по вітру.
   Реєструється як звичайний партикл-тип, без власного шейдера.

| **`isRaining()` / `isThundering()` глобальні за природою** | Затемнення неба й освітлення для спавну лишаються приблизними на сервері | M3 повертає значення з семпла в точці **гравця** (для клієнта — точно; для серверних перевірок спавну — приблизно). Це прийнято усвідомлено; поясню в README. |
| **Вітер на гравця vs античит руху** | `moved too quickly` / гумування | Прискорення від вітру застосовується **клієнтом**, а не сервером, і клемпиться нижче ванільного порогу. Значення в конфігу, з консервативними дефолтами. |
| **Sodium** | Краш або чорний екран | Не тестується (немає можливості), тому деградація агресивна: під Sodium вимикаємо власний рендер-пайплайн і нахил, лишаємо модель і фізику. |
| **Vulkan-бекенд експериментальний** | Артефакти саме на Vulkan | Уся геометрія — через Blaze3D, нуль сирих GL-викликів, тому переносимо між бекендами за визначенням. Але перевірити на Vulkan зможеш тільки ти. |
| **Детермінізм на різних JVM** | Клієнт і сервер розійшлись у стані | Тільки цілочисельні хеші (`Hashing`, splitmix64) для сідів; жодного `Math.random`, `hashCode()` рядків чи `HashMap`-ітерації в детермінованому шляху. Float-обчислення — тільки для блендингу, де дрібна різниця невидима. |
| **Оверрайди від `/set` живуть у `SavedData`** | Ростуть, якщо їх багато | Жорсткий ліміт `command.max_overrides` (дефолт 64), найстаріші витісняються; кожен має час смерті. |
